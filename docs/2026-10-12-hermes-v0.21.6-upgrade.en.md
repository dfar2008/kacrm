# Hermes v0.21.6 Upgrade Notes

**English** · [简体中文](2026-10-12-hermes-v0.21.6-upgrade.md)

This is a translated historical record of the upgrade in the source hermes-cloud project. Branches, temporary paths, test counts, and deployment status below describe that run, not the current KaCRM checkout or a new deployment.

Objective: upgrade the cloud integration from v0.21.0 to the upstream stable release v0.21.6 while preserving CRM features, custom skills, tenant isolation, human approvals, and PostgreSQL persistence.

- Previous upstream: `29112bef099274229cadff79cdff7bf7b99c4b77` (v2026.8.31).
- Target: `818c13be1dc4fd28987e1e881a9408224afd4535` (v0.21.6, a stable tag rather than canary or RC).
- Previous cloud mainline: `18724623`.
- Upgrade branch: `codex/hermes-v0.21.6-upgrade`.

## Pre-upgrade Baseline

- `scripts/upgrade-acceptance.sh`: 86 + 3 + 74 tests passed.
- Cloud suite: 1816 passed, 283 skipped.
- Isolated upstream test runner, seven patch-related files: 269 passed, four skipped.
- Tracked diffs, untracked files, and patch checksums were backed up under `/tmp/hermes-v0216-*`.

## Acceptance Requirements

1. Port and review all seven overlays individually; do not duplicate behavior already implemented upstream.
2. Preserve `schema-evolution`, `kacrm-guide`, and CRM skills; reduce only upstream-provided skills.
3. Regenerate patches and verify integrity anchors, replay on a pristine upstream checkout, and idempotency.
4. Verify the cloud SessionDB contract, upgrade acceptance, the full cloud suite, and affected upstream tests.
5. Perform local live checks for model routing, persistent sessions, tenant-specific channels, and Feishu approvals.

Status recorded at that time: local upgrade and verification completed; the upgrade branch was intended for commit and push. It had not been merged or deployed to production.

## Completed Changes

- Ported and regenerated all seven overlays. Preserved custom skills, reduced upstream skills according to provenance, and adjusted test collection based on which skills ship with the cloud distribution.
- Adapted to upstream's split gateway, agent, cron, and SessionDB modules while preserving tenant context, channel isolation, approvals, tool ACLs, callback timing, and cloud events.
- Fixed issues found during review: model credential precedence, main-profile hot-reload protection, email-origin credentials, dangling-stop retry counts, and usage accounting.
- Added PostgreSQL storage for message identity, tool identity, effect status, and model routing. Publish events only after atomic batch message commits; preserve hidden display flags, API content, and tool timing.
- Added migration `0115_agent_message_identity_routes`. Backed up the local database before migrating to 0115. The migration uses an explicit lock order and a 30-second lock timeout. Backup: `/tmp/hermes-v0216-local-db-before.dump`.
- Added truststore 0.10.4, snowballstemmer 3.1.1, tomli-w 1.2.0, and nemo-relay 0.9.3 to the external Python 3.11 environment. Updated installation markers and deployment scripts. Deployment dry-run, frontend build, and shell syntax checks passed.

These suites overlap; do not sum the passing counts. Final tests used a new isolated HERMES_HOME and an absolute HERMES_PYTHON to prevent a second managed environment introduced by the test runner from affecting the external virtual environment.

An extended SQLite check had ten additional failures that were also reproducible on the unpatched upstream version. They were recorded as environment/upstream baseline issues, not passes. Logs were stored in `/tmp/hermes-v0216-sqlite-tests.log` and the pristine comparison log.

## Local Live Checks and Limits

- Installation: `http://127.0.0.1:8765/app/`; isolated home: `/tmp/hermes-v0216-live-home`; gateway port: 9210.
- Browser sign-in succeeded. A real model replied `HERMES_V0216_OK`; subsequent tool discovery and a `todo_list` invocation succeeded with reply `TOOL_V0216_OK`.
- After refreshing and reopening the conversation from history, both replies and the tool record were still present.
- Admin-profile hot reload returned 200; main-profile default hot reload returned 409, confirming main-profile protection.
- The isolated installation was not connected to external messaging channels. Another project's gateway owned the existing Feishu connection, and it was not taken over. Real Feishu DM approval-card clicks and cross-client synchronization were therefore not tested.
- Title generation using the existing `deepseek-v4-flash-free` configuration returned 401. Chat succeeded and the title fell back to the user's prompt. The user's model configuration was not changed.
- Production was not modified. Before release, follow the deployment backup and migration procedure and verify the real Feishu channel.
